# Android architecture: Wakatta? native app (`android/`)

Status: plan, not code. Written 2026-11-23 for [ADR 0015](adr/0015-native-android-app-in-android-folder.md). Nothing here is built yet. The aim is that the implementation can be split among parallel workers (AI workers, per the bridge specs in `.agent-bridge/specs/android/`) who each own a closed set of files and never edit each other's.

Sources read: `AGENTS.md`, `GLOSSARY.md`, ADR 0013 and 0014 and 0015, `docs/BACKEND_ARCHITECTURE.md` (sections 3, 7.3, 8, 9, 11, 12), `docs/FRONTEND_REGULATIONS.md`, `docs/brand/SPEC.md`, the bridge specs `scaffold.md`, `contract-core.md`, `contract-platform.md`, `handoff-backend-additions.md`, `release.md`, the prototype `prototypes/wakatta/parts/*` and the installed Compose performance skills. The two contract files the ADR links now exist in the working tree: `docs/MOBILE_API_CONTRACT.md` (975 lines, written against the 43 paths of the earlier `docs/openapi.yaml`; another agent is refreshing it) and `docs/MOBILE_PLATFORM_CONTRACT.md` (1036 lines); both were read selectively (status legend, conventions, the screen-to-endpoint table 5.1, DTO names 6.1, version gate 3.2, polling 3.5, URL shapes 2.2). `docs/openapi.yaml` now has 64 live paths (chat, briefings and skills routers merged from `origin/main`); where this plan names an endpoint it follows that file and `backend/app/routers/*.py`, and DTO names follow `backend/app/schemas/*.py` with a `Dto` suffix. Confirm each against the refreshed contract. Branding and ADR 0013 live on `origin/main` (`docs/brand/`, `docs/adr/0013-...`), not in this working tree.

Terms are those of `GLOSSARY.md` (Foreman, Worker, Check, Sign-off, Lock, Ready, Thread, Task Board, Wakatta Status, Notice, Ask, Senpai, ...).

## Fixed by the user on 2026-11-23

1. No Google Play upload for now. The signed release APK is distributed directly and kept in `android/release/` (latest release only, plain git, no Git LFS); the keystore is never committed; one named Release Owner creates it, keeps two offline backups and builds every release APK (section 5.5).
2. applicationId is `com.techtsunagu.wakatta` and is final.
3. The release APK runs in mock mode for now: `USE_MOCK` is true in `release` and no `API_BASE_URL` is baked in. Switching to the real backend is the later package WP-REAL.
4. Push: a Contact Thread message sends a generic "New message from <name>" with no message text; Talk Threads never notify.
5. Up to 6 work packages run at the same time (section 5.4).
6. The app must be fast on low-end phones: section 6 is a hard requirement and every feature package carries a `PERF-DW` Done-when line.
7. Room 2.8.5 (not Room 3), primary blue `#1f63b5`, and no Poster role in the app for now (O-3, O-5, O-6).
8. **The backend is live (2026-11-23)**: the app is wired to the hosted API. One file, `android/core/network/.../ApiConfig.kt`, holds the base URL and every endpoint path; no other file may contain the host or an `/api/...` literal (a unit test checks it). Real repositories replace the Fakes area by area; an area with no backend route yet keeps its Fake. This overrides decision 3 above and the mock-mode release in section 5.5.

## 0. Critique of the draft scaffold brief (`scaffold.md`) and what changes

Keep: the module list idea, USE_MOCK-first, MockWebServer and ViewModel tests, no analytics SDKs, `allowBackup=false`, 48dp targets, the per-app-locale requirement, "versions pinned with the date checked".

Fix (each item is applied in this document):

| # | Problem in the draft | Fix |
| :-- | :--- | :--- |
| 1 | Feature entry takes a `NavController` (`safetyRoutes(nav)`). A feature that must open a screen of another feature then needs that feature's route class, so features depend on each other. | Every route key lives in `:core:navigation`. A feature gets a `Navigator` interface and never imports another feature (D-01, D-06). |
| 2 | `:feature:shell` holds nine unrelated screens (home, chats, board, machines, me, task, machine, notifications, onboarding). One worker, one huge file set, and it is the hub every other feature wants to touch. | Split by ownership boundary (section 3): 15 feature modules. Hub screens read other features only through small interfaces in `:core:model` (`AttentionSource`, `ThreadSource`). |
| 3 | `:core:data` is one place for repositories, and `:core:network` holds `Tri`. Every feature would edit `:core:data`; `Tri` is a domain type, not a network type. | `:core:model` (pure Kotlin) holds domain types and shared interfaces. Feature-private repositories (real and fake) live inside the feature. Only repositories used by two or more features go in `:core:data`. |
| 4 | No mention of AGP 9 built-in Kotlin. The `org.jetbrains.kotlin.android` plugin must not be applied on AGP 9 (build fails); kapt is incompatible; `kotlinOptions {}` is gone. | Toolchain section D-02 and the version table. |
| 5 | Navigation 2 "typed routes". Navigation 3 is stable (1.2.2, 2026-11-18) and has deep-link matchers since 1.2.0. | Navigation 3 (D-06). |
| 6 | `explicitNulls=false` and `encodeDefaults=false` for every request. `PUT /shift-assignments` sends `{workerId: null}` to clear a slot, and `PATCH` bodies distinguish "absent" from "null". The settings would silently drop a meaningful `null`. | Request DTOs are built per call; fields where `null` means something use `@EncodeDefault` or a dedicated `Json` with `explicitNulls=true` (D-03, section 4 rule R-4). |
| 7 | "ETag/If-None-Match support" left vague. The backend sends `Cache-Control: no-store` on authenticated JSON (`BACKEND_ARCHITECTURE.md` section 12), so OkHttp's HTTP cache will never store the body and never revalidate. | A manual `ConditionalGet` helper: the cached body and ETag live in a `CacheStore` (Room); a 304 returns the cached body (D-03, D-04). |
| 8 | "401 handling" would also fire on a wrong PIN, because `POST /auth/login` returns 401 `UNAUTHORIZED` for a wrong PIN. | The session-expired handler ignores `/auth/login`; a wrong PIN is a normal `AppError.WrongPin` (D-09). |
| 9 | `USE_MOCK` is a build-time flag, false in release, with no word on how a mock demo is distributed. AGENTS.md 4.1 and F-42 want the demo never to break. | `release` is mock for now (user decision) and carries no `API_BASE_URL`; `-Pwakatta.useMock` and `-Pwakatta.apiBaseUrl` override locally; WP-REAL flips release to the real backend later (D-10, 5.5). |
| 10 | The Compose UI test is an instrumented test, which AI workers and CI cannot run without an emulator. | Compose UI tests run on Robolectric inside `testDebugUnitTest`; instrumented tests exist only for Macrobenchmark and a smoke test (D-11). Robolectric has no `AndroidKeyStore`, so the token-store test uses a fake `Aead` (the Tink wiring is tested on a device in the smoke test). |
| 11 | detekt 1.23.8 is the stable line and targets older Kotlin; the Kotlin 2.4 compatibility is not documented. detekt 2 is alpha (`dev.detekt:detekt-cli:2.0.0-alpha.6`). | Spotless + ktlint + Android Lint + compose-lint-checks block the build; detekt is not adopted until 2.x is stable (D-12). |
| 12 | "Done when `git status --short -- . ':!android'` shows no changes" cannot pass: the working tree is already dirty (many files modified by others). | Scope guard compares the changed-file list with the work package's globs (`android/tools/scope-guard.sh`, section 5). |
| 13 | No Poster role and no Panel-device session. The prototype guards `notice-new` with `isPoster = () => FM`, but the backend has a separate Poster (district code, 6-digit PIN) and a Panel device token (180 days, read-only, one Machine). | Open questions O-3 and O-4; the session model carries a role and an optional panel token (section 4). |
| 14 | Wrapper bootstrap says "download a Gradle distribution", with no integrity check. | Wrapper pinned to Gradle 9.6.0 with `distributionSha256Sum`; the worker verifies the hash (D-02). |
| 15 | Bengali and Japanese fonts: "choose system vs bundled" with no rule for which glyph set Japanese text gets inside an English UI. | D-08: system font for ja, one bundled subset for bn, and a locale tag on every text by the content language. |
| 16 | No performance requirement at all. | Section 6 (rules, budgets) and section 5 (performance work packages). |

## 4. Shared contracts

Everything a feature codes against is an interface or type in `:core:model` (pure Kotlin) or `:core:common`. WP-0A writes them first, from this section; after WP-0A they are frozen. A feature that needs another member or another shared type does not edit the module: it files a Contract Change Request (CCR), a new file `android/contract-requests/<WP>-<n>.md` (one file per request, so requests never conflict) with the exact signature, the reason and the screens that need it. The lead applies approved CCRs in one commit and tells the affected work packages. Until then the worker uses a feature-private adapter.

### 4.2 Rules every module follows

| ID | Rule |
| :-- | :--- |
| R-1 | Ids are strings, never parsed as numbers. Timestamps are ISO 8601 UTC parsed to `java.time.Instant`; dates and times are shown in Asia/Tokyo (no daylight saving time). |
| R-2 | Every repository interface has a `Real` (Retrofit) and a `Fake` (seeded, latency 200 to 600 ms) and one abstract contract test class that both pass. |
| R-3 | A Worker-facing model has no field for the right answer (`correctIndex`). Grading and Wakatta Status come from the server; a Fake computes them inside the Fake, never in a ViewModel or composable. A reflection test asserts the field is absent. |
| R-4 | Request DTOs: no field relies on a serialization default; a field where `null` means "clear" (for example `PUT /shift-assignments` with `workerId: null`) uses `@EncodeDefault` or the repository's `explicitNulls=true` `Json`; PATCH bodies are built from the fields the user changed. Unknown fields are never sent (the backend returns 422: `extra=forbid`). |
| R-5 | One user action, one Idempotency-Key (UUID) made in the ViewModel, passed down, stored in the outbox row before the first attempt, reused on every retry. Required on Checks, Note, Briefing and Notice drafts, Asks, Near-miss Reports and chat messages; a missing key is 422. |
| R-6 | Polling uses `ConditionalGet` (ETag sent back verbatim, 304 returns the cached body; the server compares the string exactly), runs only while the screen is visible and stops in the background, with the intervals of `docs/MOBILE_PLATFORM_CONTRACT.md` 3.5: Machine Panel 2 s, Foreman Board 5 s, Thread messages 2 s (proposal: 5 s after 30 s of only 304), Thread list 10 s, Task Board 5 s, Notices, Events, Asks and Briefings on open and every 60 s, `/app/config` at cold start and after 1 h; back off 2, 4, 8, 16, 30 s on errors; one immediate request on resume and after a push. |
| R-7 | Repositories return `AppResult` or `Flow<AppResult>` and never throw for expected failures; ViewModels map errors to `UiState.error` and never show raw codes (F-05). |
| R-8 | No text literal in code: strings are resources prefixed by module; content translated by the server is shown with `TriText` and the content language tag (D-08). |
| R-9 | UI: 48dp minimum touch targets, 16sp minimum body text, a confirmation step before Approve, Assign and Report (F-26), colour never the only signal (F-35), loading, empty and error state on every screen (AGENTS.md 4.1, F-31). |
| R-10 | Kotlin visibility: `internal` by default; public only the feature entry (`xEntries`), its Hilt module and the interfaces it implements. Functions under 50 lines. No `println`, no logging of tokens, PINs, Ask text or transcripts (BACKEND_ARCHITECTURE.md section 12). |
| R-11 | Writes that decide safety are online only: Check, approve, publish, Panel Override, Task move. Queueable writes are listed in D-04. |
| R-12 | The session gate: no screen except sign-in and change-PIN renders without a `Session`; `403 PIN_CHANGE_REQUIRED` goes to change-PIN; `401` outside `/auth/login` clears the session. A shared phone's "Not me" calls logout (`POST /auth/logout`) and clears local caches (`BACKEND_ARCHITECTURE.md` 3.1). |

## 5. Work packages

Concurrency: at most **6 work packages in progress at any time** (lead's correction of 2026-11-23). Each package owns the globs listed; no glob appears in two packages that can run at the same time (checked by `tools/scope-guard.sh`). The only repeats are hand-overs between packages that never overlap in time: `android/app/**` is WP-0A's first and WP-INT's last (WP-INT runs alone), and WP-REAL edits two `:app` files after WP-INT. Sizes are estimates for one worker: S about half a day, M about a day, L two to three days. They are not measured.

### 5.1 Definitions used in every Done-when

- `GATE(<module>)` = `cd android && ./gradlew :<module>:spotlessCheck :<module>:lintDebug :<module>:testDebugUnitTest :<module>:assembleRelease && tools/check-module.sh :<module>` exits 0. `check-module.sh` runs `checkModuleGraph`, the screen-coverage check and the performance checks of section 6.
- `PERF-DW` (every feature package carries this line): `tools/check-module.sh :feature:<x>` reports, for the release build, (a) every `*Screen`, `*Content` and `*Item` composable in the module as restartable and skippable in the Compose compiler report, or listed with a reason in `feature/<x>/perf-allowlist.txt`; (b) every `items(` and `itemsIndexed(` call passes `key` and `contentType`; (c) none of the banned calls of rule P-18 appears; (d) no Retrofit, Room, DataStore or file call appears in a composable (repositories use injected dispatchers).
- `SCOPE(<WP>)` = `tools/scope-guard.sh <WP>` exits 0: the files changed since the package's base commit are all inside the package's globs (the working tree already has unrelated changes, so the check lists changed files against the globs; it does not require a clean tree).
- `SCREENS` = `python android/tools/check-screens.py` exits 0. `android/screens.json` is written once by WP-0A from section 3.2 (screen id, module, route key); the script fails if a screen id of `prototypes/wakatta/parts/*.screens.html` has no entry, if a route key is missing from `:core:navigation`, or if the module has no entry function for it.

### 5.2 Common rules to paste into every worker spec

1. Edit only your globs; if you need a change elsewhere, write a CCR (section 4) and stop that part.
2. Do not add dependencies; `libs.versions.toml` is frozen (WP-0A). Ask by CCR.
3. Read section 3.2 row(s), section 4 and section 6 of `docs/ANDROID_ARCHITECTURE.md` before starting. Port behaviour from the named prototype functions; do not copy the prototype's grading or fake AI into non-Fake code.
4. Every repository: interface, Fake, Real, one contract test for both. Real may stay unconnected when the backend XREQ is pending: ship Fake, keep Real compiling against MockWebServer fixtures.
5. No attribution to any AI tool or vendor in any file, comment, metadata or build config. No commits or pushes by workers; the lead integrates.
6. Report: files changed, the Done-when command and its last 15 lines, what is not done.

### 5.5 Release build and the in-app update path (direct APK, no Google Play)

Decided by the user on 2026-11-23: no Google Play upload for now; the applicationId `com.techtsunagu.wakatta` is final; the signed release APK is distributed directly and kept in the repository under `android/release/` with plain git (no Git LFS); the keystore is never committed; **the release APK runs in mock mode for now** (the real-backend switch is the later package WP-REAL).

**Release Owner.** One named person (the lead names them: O-19) creates the release keystore with `keytool`, keeps two offline backups outside the repository and outside the build machine, and builds every release APK. Workers never hold the keystore; the Release Owner's machine or a CI secret is the only place the signing step runs. WP-REL builds and tests the tooling with a throwaway keystore.

**Files and ignore rules.** `android/.gitignore` ignores `build/`, `.gradle/`, `local.properties`, `*.jks`, `*.keystore`, `keystore.properties`, `.idea/`, `captures/` and does **not** ignore `release/*.apk`, `release/*.sha256`, `release/latest.json` or `release/*-mapping.txt`. The root `.gitignore` has no APK or keystore rule (checked 2026-11-23). `android/release/` keeps only the latest release: `wakatta-<versionName>.apk` and `wakatta-<versionName>.apk.sha256` (user decision). Two further files are architect additions the lead may veto: `wakatta-<versionName>-mapping.txt` (R8's `mapping.txt`; without it a release crash stack cannot be read, and there is no Play Console) and `latest.json` (the update manifest, below). The release script deletes the previous release's files. Plain git still keeps old APKs in history (K-10).

**Build.** `cd android && tools/release/build-release.sh` runs `./gradlew assembleRelease` with the signing key supplied from outside the repository: either `android/keystore.properties` (ignored; `storeFile` is a path outside the repository, plus `storePassword`, `keyAlias`, `keyPassword`) or the environment variables `WAKATTA_KEYSTORE_FILE`, `WAKATTA_KEYSTORE_PASSWORD`, `WAKATTA_KEY_ALIAS`, `WAKATTA_KEY_PASSWORD` (a CI secret holds the keystore as base64 and the workflow decodes it to a temporary file). When neither is present, `assembleRelease` still builds, unsigned, so workers and CI without the secret do not fail; the signing configuration is written once, in WP-0A. The script reads `versionName` and `versionCode` from `android/version.properties` (the one place; `versionCode` rises by one per release), copies the signed APK to `android/release/wakatta-<versionName>.apk`, writes the checksum file in `sha256sum` format (`<64 hex>  wakatta-<versionName>.apk`), copies `mapping.txt`, writes `latest.json`, deletes the previous release's files, and verifies the result with `apksigner verify --print-certs` and a recomputed checksum. Release `abiFilters` are `arm64-v8a` and `armeabi-v7a` (phones only; effect on size UNVERIFIED).

**Mock mode in the release APK.** `BuildConfig.USE_MOCK` is true in `release`; `API_BASE_URL` is not baked in (empty); every repository uses its Fake (D-10). Consequences the lead should know: nothing a user does is saved on a server; there is no push (FCM needs the backend); sign-in works against the Fake roster; the only network call is the update check below.

**In-app update.** The version gate in `docs/MOBILE_PLATFORM_CONTRACT.md` 3.1 and 3.2 is the `X-App-Version` and `X-App-Platform` headers, a public `GET /api/app/config` returning `android.minSupportedVersion`, `android.latestVersion` and `android.storeUrl` plus a maintenance block, and `426 UPGRADE_REQUIRED`. Those are planned, not built, and in mock mode there is no API base URL. So the update check has two sources behind one interface `AppConfigRepository`: (a) in mock mode, a static manifest at a fixed `UPDATE_MANIFEST_URL` (a `BuildConfig` field, separate from `API_BASE_URL`; the file is `android/release/latest.json` with `versionName`, `versionCode`, `apkFile`, `sha256`, `minSupportedVersionCode`); (b) after WP-REAL, `GET /app/config`, where `android.storeUrl` (a Play URL in the contract example) is reused as the APK URL and one more field, the APK SHA-256, is a backend ask (B-1). Where `latest.json` and the APK are hosted is open (O-17). The flow in `:feature:update`:

1. After the first frame, and whenever a call returns 426, `AppConfigRepository` is read and the `VersionGate` (interface in `:core:model`) becomes `UpToDate`, `Soft` (a newer version exists: a dismissible card on Home and Me) or `Hard` (below the minimum, or 426: a blocking `UpdateKey` screen; sign-out stays possible). `:core:network` maps 426 to `AppError.UpgradeRequired` and calls `VersionGate.require()`.
2. The Update screen downloads the APK over HTTPS to the app cache with OkHttp (progress, cancel), computes SHA-256 and refuses on mismatch. A checksum from the same host proves integrity, not authenticity; authenticity comes from Android refusing an update signed with a different certificate.
3. It installs through a `PackageInstaller` session. The app declares `REQUEST_INSTALL_PACKAGES`; if `canRequestPackageInstalls()` is false it sends the user to the system "Install unknown apps" screen for this app and back. The system asks the user to confirm (`STATUS_PENDING_USER_ACTION`); a silent self-update is not generally possible (PackageInstaller reference, read 2026-11-23; the Android 12 and later conditions for skipping the prompt were not read in full). An update must have the same package name, the same signing certificate and a higher `versionCode`.
4. The Fake `AppConfigRepository` (debug) returns a newer version and simulates the download, so the screens are built and tested without a server or a real APK.

**Push (user decision).** A Contact Thread message produces one generic notification, "New message from <name>" (translated into the account language on the device), with no message text in the payload or the notification. Talk Threads never notify. Other push types follow the platform contract. Push stays inactive in the mock-mode release.

Play-only work from the earlier plan is dropped: Play App Signing and upload keys, AAB and `bundletool` sizing, Data safety form, store listing, testing tracks, the Play target-API deadline as a gate. Kept from `release.md`: privacy policy (APPI), the permission rationale texts, the support contact and the device matrix.

## 6. Performance (hard requirement)

The app must be fast, efficient and snappy on low-end phones: a factory worker opens it with a gloved hand at a Machine, and the Machine Panel and the Check must appear without waiting. Performance is part of "done" for every package (the `PERF-DW` line of 5.1), not a later polish step.

Inputs: the installed skills `auditing-compose-performance`, `jetpack-compose-performance` (Google, last updated 2026-11-10), `configuring-r8-for-compose`, `generating-baseline-profiles`, `diagnosing-compose-stability`, `stabilizing-compose-types`, `using-strong-skipping-correctly`, `deferring-state-reads`, `optimizing-lazy-layouts` and `testing-compose-in-release-mode` (all in the user's local skills folder). The other skills in that folder are not performance sources for this app: `android-compose-design`, `material-3` (design), `navigation-event` (predictive back, used in D-06), and `performance`, `web-perf`, `core-web-vitals`, `memory-leak-debugging` (web and JavaScript only). Workers cannot load these skills, so 6.1 restates the rules to paste into every spec. Where two skills disagree, this plan follows the newer Google skill (see P-05).

Figures such as "about 75 percent faster startup and 60 percent better frame rendering from debug to release" and "about 30 percent faster cold start and 40 percent smoother first scroll from Baseline Profiles" are quoted by those skills from Android Developers sources; they were not measured on this project and are not budgets.

### 6.1 Performance rules (paste into every worker spec)

| ID | Rule |
| :-- | :--- |
| P-01 | Measure and read Compose compiler reports only on release-derived builds (`release` or the `benchmark` variant) on a real phone. Debug numbers and debug reports are not evidence. Every number is quoted with variant, device, compilation mode and iteration count. |
| P-02 | R8 full mode is on for `release`: `isMinifyEnabled = true`, `isShrinkResources = true`, `getDefaultProguardFile("proguard-android-optimize.txt")` (not `proguard-android.txt`). No Compose-wide keep rule (never `-keep class androidx.compose.** { *; }`). Add a keep rule only for what `missing_rules.txt` or a release crash names, as narrow as possible. `kotlinx.serialization` and Hilt plugins emit their own rules; verify, do not duplicate. WP-0A records whether AGP 9.5 uses `isMinifyEnabled` or the newer `optimization { }` DSL. |
| P-03 | Ship a Baseline Profile and a Startup Profile. The generator journeys cover cold start and the first scroll of Chats and Machines, not startup alone. Depend on `profileinstaller`. The package must contain `assets/dexopt/baseline.prof`. Availability of the Startup Profile option in the `androidx.baselineprofile` 1.5.0 plugin: UNVERIFIED, WP-PERF-A confirms or drops it. |
| P-04 | Lazy lists: every `items(...)` and `itemsIndexed(...)` passes `key = { it.id }` (the server's stable string id, never the index, never a random value, never `hashCode()` of a mutable object) and `contentType = { ... }` (a stable discriminator such as an enum or the class) for mixed lists. Use `itemsIndexed`, not `indexOf`. Use a plain `Column` or `Row` for bounded lists of about 10 items or fewer. Hoist `painterResource`, colours and shapes above the `items` lambda. Resolve `LocalContext`, `LocalDensity` and similar once above the list. No `BoxWithConstraints` or `SubcomposeLayout` in an item. No `LaunchedEffect` or `DisposableEffect` for impressions inside an item (items are pre-composed off screen). `Modifier.animateItem()` only with a `key`. |
| P-05 | UI state is a flat immutable `data class` of `val` primitives, `String`, enums, nested classes of the same kind, and `List<T>`. No `var`, no `MutableList`, no `Flow`, no ViewModel, no `java.time` object in UI state (preformat to `String` or keep epoch `Long`). Strong skipping stays on (default on Kotlin 2.0.20 and newer); never add a `StrongSkipping.disabled()` flag. Do not annotate a model that holds a collection with `@Stable` or `@Immutable`, and do not add `kotlinx-collections-immutable`: Google's skill says an `O(N)` `equals()` on a large list on every pass costs more than instance equality. The older `stabilizing-compose-types` skill advises `ImmutableList` instead; we follow the Google skill and re-test with the compiler report. Produce a new `List` instance only when the content changed (map once in the ViewModel). A class from a module without Compose that the report calls unstable gets `@Stable` or `@Immutable` through `androidx.compose.runtime:runtime-annotation` only if it truly honours the contract. |
| P-06 | No work in composition. A composable body does not sort, filter, map large lists, run a regex, parse JSON, format dates, build a `Path`, `Brush` or formatter, or touch IO. Do it in the ViewModel, or in `remember(<every input read inside>)`. Never pass snapshot-state values as `remember` keys. Do not wrap a synchronous value in `remember { mutableStateOf(...) }` just to overwrite it at once. |
| P-07 | `derivedStateOf` (or `computedStateOf` on Compose 1.13, symbol to be confirmed by the worker in the official docs) only when the input changes more often than the result, for example `listState.firstVisibleItemIndex > 0`. A plain getter for a trivial boolean. Do not use `produceState` plus `snapshotFlow` to watch scroll position. Read a collection's `.size` directly. |
| P-08 | Defer state reads. Anything that changes every frame (scroll or drag offset, animated alpha, scale, translation, the Panel sweep, the Auto-send Countdown ring) is read inside a lambda modifier: `Modifier.offset { }`, `graphicsLayer { }`, `drawBehind { }`, `drawWithCache { }`, `Modifier.layout { }`. Pass such values to children as `() -> T`. Never feed an animated `State` to `Modifier.alpha(x)`, `rotate`, `scale` or `offset(x.dp)`. Animate only transform, alpha and draw properties. |
| P-09 | Hoist lambdas. A screen passes `onEvent: (UiEvent) -> Unit` and ids; a lazy item receives the item and one `onEvent`, not a lambda per item that captures other state. Strong skipping memoises lambdas written inside composable scopes; a lambda made in a non-composable scope (a builder, a list `map`) is not memoised. `@DontMemoize` and `@NonSkippableComposable` need a comment saying why. |
| P-10 | Flow collection: `collectAsStateWithLifecycle()` once per screen, in `XScreen`, never in `XContent` and never per item. ViewModel state is `StateFlow` built with `stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), initial)`. A composable never takes a `Flow` parameter. |
| P-11 | The main thread draws and handles input only. Room, DataStore, file access, JSON parsing, image decoding, Tink, ML Kit setup, TextToSpeech init and the camera run off it through injected dispatchers (`@IoDispatcher`, `@DefaultDispatcher`, qualifiers in `:core:common`). Repositories wrap blocking work with `withContext`. `runBlocking`, `Thread.sleep` and `GlobalScope` are banned. |
| P-12 | Startup: `Application.onCreate` only builds the Hilt graph. No network, database, Tink keyset, font loading or SDK init there. Heavy singletons are `Lazy<T>` or `Provider<T>`.
