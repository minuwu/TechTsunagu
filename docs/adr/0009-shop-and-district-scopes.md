# Two data scopes, shop and district, isolated in the repository layer

Wakatta? serves many factories from one database. Work data (Machines, Note Versions, Checks, Sign-offs, Briefings, Near-miss Reports, Senpai pairs, Asks) belongs to a **shop** and carries `shop_id`. Life data (Posters, Notices, Events) belongs to a **district** and carries `district_id`, because a 自治会 or city serves Workers of several employers; a Worker belongs to one shop and lives in one district. Isolation is enforced in two places: every query goes through `app/repositories/`, which takes the session's scope and adds it to every statement (no unscoped method exists, and import-linter keeps queries out of services); and every reference between rows of one scope is a composite foreign key `(shop_id, x_id) → x (shop_id, id)`, so the database itself rejects a row that points into another shop. An id from another scope returns 404. We rejected Postgres Row Level Security: with a pooled synchronous session it needs `SET LOCAL` in every transaction and `FORCE ROW LEVEL SECURITY` for the owning role, and a mistake fails silently, while the filter plus a two-shop isolation test suite gives a guarantee we can prove in CI. We rejected schema-per-tenant because migrations and the shared district data would multiply. This supersedes v1's "one shop, no tenants" note.
